# 에이전트 2 (Evidence Extraction) 인계 문서

작성 2026-10-06. 합성 데이터·정답(②·④) 담당이 에이전트 2를 맡으며 남기는 문서입니다. 이 문서와 `SKILL.md`, `common_format_v0.5.md`만 읽으면 이어서 만들 수 있게 정리했습니다.

## 1. 프로젝트 한눈에

환자-임상시험 매칭 멀티 에이전트 시스템 (대회 과제). 평가: 매칭 정확성 30%, 랩 정성 평가 30%, 발표 40%. 대회는 "역할을 나눈 에이전트들이 스스로 계획하고 도구를 써서 근거에 기반한 판단"을 보길 원하고, 단일 챗봇은 감점 대상입니다.

```
ClinicalTrials.gov → 조건 기반 시험 후보 조회
  → 1. Trial Parsing Agent        ⓪ → ① 구조화 기준        (CT.gov 담당, ①-b 진행 중)
  → 2. Evidence Extraction Agent  ② → ③ 환자 근거          ← 이 문서
  → 3. Eligibility Reasoner       ① + ③ → 기준별 PASS/FAIL/UNKNOWN/CONFLICT
        (Evidence Graph / Shared Reasoning State)
  → 4. Evidence Verifier          근거 검증 → 문제 있으면
  → 5. Information Agent          추가 정보 획득 → 근거 그래프 갱신 → 재평가
  → 6. Recommendation Agent       시험 순위 + 근거 사슬 → 웹 화면
```

## 2. 에이전트 2가 하는 일

입력: 환자 한 명의 기록 ② (날짜·출처가 붙은 문서 목록), 선택적으로 후보 시험들의 구조화 기준 ①-b.
출력: 근거 객체 ③ 목록. 형식은 `common_format_v0.5.md` 5장.

```json
{"evidence_id": "SYN-0007-EV03", "patient_id": "SYN-0007", "concept": "free_t4", "value": 3.9, "unit": "ng/dL",
 "value_type": "numeric", "observed_date": "2026-09-03", "certainty": "confirmed", "subject": "patient",
 "source": {"doc_id": "SYN-0007-D02", "doc_type": "lab_result", "author_role": "lab", "span": [17, 34], "text": "free T4 3.9 ng/dL"},
 "extracted_by": "rule"}
```

반드시 지킬 원칙 (형식 문서와 정답 규칙에서 옴):

- **기록 없음은 음성이 아니다.** 기록에 명시적으로 "없다"고 적힌 경우만 `value: false` 근거를 만든다 ("No prior malignancy", "NKDA", "never smoker"). 언급이 없으면 근거를 만들지 않는다.
- **`source.span`은 문서 `text` 안의 정확한 문자 위치** (끝 미포함). `source.text == document.text[span[0]:span[1]]`이 항상 성립해야 한다. LLM이 준 인용문은 그대로 믿지 말고 위치를 다시 찾는다 (공백·NBSP·"..." 차이 주의).
- **날짜**: `observed_date`는 검사·투약이 실제로 일어난 날. 문장에 날짜가 없으면 문서 날짜. "3일 전"은 문서 날짜 기준으로 계산. TREC처럼 가려진 날짜(`[**2101-3-4**]`)나 비현실적 날짜는 `null`. 기준일 `as_of`(합성 2026-10-01, TREC 2021-04-27)를 기준으로 모든 기간을 계산하며 실행하는 날은 쓰지 않는다.
- **확실성**: 검사·병리·영상은 `confirmed`, 환자 진술은 `reported`, "suspected", "possible", "features of", "rule out"은 `suspected`. 의심은 진단이 아니다 (에이전트 3이 이 구분으로 UNKNOWN을 낸다).
- **주체**: 가족 이야기("어머니 유방암")는 `subject: "family"`.
- **계획·논의는 받은 치료가 아니다.** "Options discussed: A vs B", "plan to start", "consider"는 시행 이력으로 추출하지 않는다 (필요하면 `certainty: "suspected"`가 아니라 아예 다른 개념 "planned"로 구분하거나 제외).
- **개념 키**는 `concepts.json`에 있는 것만. 수치는 개념의 기본 단위로 변환.

## 3. 다른 에이전트와의 연결

| 상대 | 주고받는 것 | 메모 |
| --- | --- | --- |
| 1 (Trial Parsing) | ①-b의 `concept`, `answerable_by`, `time_window` | 후보 시험이 필요로 하는 개념 목록 = 무엇을 찾을지 계획하는 재료. ①-b가 오기 전에는 임시 개념 목록으로 개발 |
| 3 (Reasoner) | ③ 목록 (Evidence Graph에 들어감) | 3은 ③만 보고 판정하는 것이 원칙. 근거가 빠지면 3이 UNKNOWN/MISSING을 내므로 재현율이 가장 중요 |
| 4 (Verifier) | "이 근거가 기록과 안 맞음 / 날짜가 이상함" 피드백 | 해당 문서·개념만 다시 추출 |
| 5 (Information) | 환자 답변·추가 검사 결과 | 새 문서(`type: "patient_interview"`, `author_role: "patient"`)로 기록에 붙이고, 그 문서만 추출해 그래프 갱신 |

## 5. 채점

`code/eval_evidence.py`:

```
python3 code/eval_evidence.py --gold data/dev/gold/gold.jsonl --pred runs/dev_v1/evidence.jsonl --patients data/dev/input/patients.jsonl --by doc_type
```

- **재현율 (주 지표)**: 정답 근거와 같은 문서에서 위치가 겹치는 예측이 있는 비율. IoU 0.5 이상(위치 정확도)도 같이 나옴
- **개념·값 일치**: 정답 `concept`·`value`가 채워진 근거에서 (①-b 이후)
- **환자당 예측 수**: 정답 근거는 판정에 쓰인 것만 있어서 정밀도를 직접 계산할 수 없음. 너무 많이 뽑으면 3번의 입력이 시끄러워지므로 함께 봄
- **최종 효과**: 3번에 ③을 넣었을 때 기준 판정 정확도 (기록 원문을 직접 줬을 때와 비교)
- 변형 세트(공통 형식 7장)가 생기면: 미끼 근거(`decoy_evidence`)를 근거로 뽑지 않는지, 날짜를 옮긴 검사의 `observed_date`가 맞는지

## 6. 설계 초안

| 단계 | 하는 일 | 방식 | 에이전트다운 점 |
| --- | --- | --- | --- |
| 1. 계획 | 후보 시험 ①-b의 개념 목록과 `answerable_by`로 찾을 대상 정하기. 없으면 기본 목록(진단, 약물, 주요 검사, 수행 상태, 임신, 흡연, 알레르기) | 코드 | 시험마다 다른 추출 계획 |
| 2. 추출 | 검사 수치: `concepts.json`의 `aliases` + 숫자·단위 패턴 (규칙). 질환·약물·시술·부정 표현·가족력·계획/논의 구분: LLM (JSON 출력, 문장 단위 인용) | 규칙 + LLM | 도구 선택 |
| 3. 위치 | 인용문 → 문서 내 정확한 span (`gold_lib.locate` 재사용) | 코드 | |
| 4. 날짜·단위 | 문서 날짜, 상대 날짜, 가려진 날짜 → `observed_date`. 단위 변환 (`alt_units`), 계산기(eGFR CKD-EPI, BMI, 나이) | 코드 (도구) | 계산은 코드로 |
| 5. 자체 검사 | span 일치, 값 범위, 날짜 ≤ as_of, 중복 제거. 실패한 것만 다시 추출 | 코드 + 재시도 | 자기 수정 |
| 6. 갱신 | 4번 피드백·5번 새 정보가 오면 해당 문서/개념만 다시 추출 | 루프 | 재계획 |

**모델 결정 (2026-10-06)**: 개발은 OpenRouter gpt-oss-120b, 최종은 Claude Haiku 4.5 + Message Batches API + 프롬프트 캐시. 모델을 바꾼 뒤 dev로 다시 확인·조정한다. API 키는 이 작업 공간에 두지 않고 팀원 PC에서 실행한다 (`agent2/RUN_LOCAL.md`). 기획안은 Patient Profiler에 작은 모델(haiku 급)을 권장. 정답 달기에는 OpenRouter gpt-oss-120b를 썼고 비용이 낮았음 (예: 기준 1,072개 행정 항목 분류에 약 1센트. 각 스크립트가 실행 끝에 실제 토큰과 금액을 출력함).

LLM 호출 시 겪은 문제 (같은 문제를 피하려면):
- OpenRouter 응답이 keep-alive 공백만 보내며 멈출 수 있음 → `gold_lib.call_llm`의 전체 시간 제한(`LLM_DEADLINE`, 기본 240초) 사용
- 같은 문장을 반복하며 출력 한도까지 가는 경우 → `max_tokens` 상한
- 모델이 문자열 대신 리스트를 주는 경우 → 필드 타입 검사 후 재요청
- OpenRouter에서 빠른 제공자 우선(`throughput`)은 비용이 크게 늘어남 → 기본 라우팅 사용
- zsh에서 명령에 `#` 주석이나 `!`를 넣으면 오류

## 8. 지켜야 할 규칙

- **test 블라인드**: 개발자는 test 정답 검수에 참여했으므로, 개발·프롬프트 수정은 dev와 TREC로만 한다. test 평가는 스크립트로 한 번 돌리고, 결과를 보고 다시 고치지 않는다. 보고서에 이 사실을 밝힌다.
- `id_map*.json`(환자 번호 → 기본 환자 ID)과 정답 파일은 에이전트 입력에 넣지 않는다.
- 판정은 에이전트 3의 일. 에이전트 2는 사실만 뽑고 "이 기준을 만족한다" 같은 판단을 출력하지 않는다.

## 9. 진행 순서

- [x] 1단계 (①-b 없이): 임시 개념 목록 20~40개 (dev 기준 문장에서 자주 나오는 것) → 추출 + 위치 + 날짜 → dev 재현율 측정 (목표: any-overlap 0.85 이상)

  - 계획 단계: TF-IDF로 후보 시험 20개(판정 대상 시험 54개 중 top-15에 49개) → 그 기준 문장의 어휘로 일반 근거(소견·기타 검사) 거름. 계획 없이 돌리면 0.979 / 환자당 179개
  - 위치 상한: 문장·줄·항목 단위로 전부 내도 IoU≥0.5는 0.83 (정답 위치 단위가 들쭉날쭉)
  - 남은 한계: 개수가 정답(환자당 32개)의 5배 → ①-b 개념 계획과 LLM 관련성 판단으로 줄일 것. 계획/논의·복약 순응도·불명확한 소견은 LLM 몫

- [x] 1.5단계: LLM 층 (`agent2/llm_layer.py`). gpt-oss로 개발(v5~v10) 후 최종 모델은 Claude Haiku 4.5 배치(v11~), `--relevance criteria`
- [x] 1.6단계 (속도·성능 균형, v3~v7): 확실한 규칙 단위는 LLM 생략, 짧은 출력(`ok`·기본값 생략), 요청 30단위·환자 내 병렬, `--online` 지연 측정. gpt-oss 실측 대기

성능과 속도의 균형을 최우선으로 한다. 사용자가 느리다고 느끼면 서비스 품질이 떨어진다.
- 사용자가 기다리는 경로(온라인): 일반 API 호출 + 환자 내 요청 병렬. 배치 API는 최대 24시간이 걸릴 수 있어 쓰지 않는다
- 오프라인: 등록된 환자 기록의 전체 추출, dev/test 평가는 배치 + 캐시 (50% 가격)
